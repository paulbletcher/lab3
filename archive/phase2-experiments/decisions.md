# Technical decisions

This log records completed decisions for the Kloud Kart DE03 SQL lab. The [diagnosis](diagnosis.md) holds the detailed integrity findings; [test results](test_results.md) holds verification evidence. Add later decisions here when their design is agreed and distinguish implementation from verification.

## Decision 001 — Preserve historical data

**Status: Adopted.** Historical records are preserved while their integrity problems remain visible.

### Context and decision

The diagnosis identified negative stock balances, missing references, inconsistent order totals and statuses, and other issues. These findings establish discrepancies, but they do not establish the correct replacement values or the original business events. Some observations, such as free items, shared email addresses, and zero-change stock takes, may be legitimate.

We chose not to delete, overwrite, merge, or arbitrarily correct historical records without sufficient business evidence. Investigations may require payment records, original orders, promotion rules, product-retirement information, or physical inventory counts.

### Reasoning and consequences

Deleting orphaned order items would remove evidence of historical purchases. Assigning them to an unrelated order would create a false sales history. Replacing missing prices with current catalog prices or overwriting stored totals could misrepresent the amount originally charged. Setting negative stock to zero could hide an unresolved inventory discrepancy.

For Kloud Kart, preserving this evidence supports reliable customer-spending analysis and an inventory trail that can be investigated. Reports will need explicit, documented handling of unresolved records, and any later correction must be supported by evidence.

Preventing new faults and correcting historical faults are separate responsibilities. Future checkout validation, stock controls, and audit behavior can protect new transactions without assuming that existing records have been repaired. The identity migration in Decision 002 changes ID-generation metadata and sequence state while preserving existing row values; it does not resolve the diagnosed integrity problems.

## Decision 002 — Concurrency-safe automatic ID generation

**Status: Implemented; identity metadata and initial sequence state verified. Concurrent ID generation has not been load-tested.**

### Context

The original [schema.sql](../schema.sql) defines ordinary `integer` primary keys without automatic generation for `orders.order_id`, `order_items.order_item_id`, and `inventory_log.log_id`. Concurrent checkout requests need unique IDs for purchases, their items, and inventory movements without coordinating counters in application code.

### Alternatives considered

| Alternative | Advantages | Disadvantages and assessment |
|---|---|---|
| `MAX(id) + 1` for every insert | Simple to understand; no extra schema object. | Concurrent requests can calculate the same ID, causing primary-key conflicts. Serializing that calculation adds contention. A table's maximum also misses historical orphan references. Rejected for per-insert allocation. |
| Manually managed PostgreSQL sequences | Safe allocation across sessions; flexible naming and configuration. | Requires explicitly wiring the column default and managing sequence ownership and lifecycle. Viable, but adds manual setup for this lab. |
| PostgreSQL `SERIAL` | Familiar shorthand for an owned sequence and a default. | PostgreSQL-specific column-definition shorthand; retrofitting existing columns requires arranging the equivalent sequence/default behavior. Identity expresses the selected behavior directly on the existing columns. |
| `GENERATED ALWAYS AS IDENTITY` | Automatic allocation with stronger protection against accidental explicit IDs in `INSERT`. | Explicit IDs in `INSERT` require `OVERRIDING SYSTEM VALUE`. Viable, but less convenient for deliberate explicit-ID inserts. |
| `GENERATED BY DEFAULT AS IDENTITY` | Standard identity syntax, automatic allocation, and ordinary explicit-ID insertion when required. Can be added to the existing integer columns. | Explicit IDs can collide with generated values or leave a sequence behind imported IDs. Selected with that responsibility documented. |

`SERIAL` expands into a sequence-backed default. Identity is the SQL-standard alternative. `ALWAYS` and `BY DEFAULT` differ in how explicit `INSERT` values are accepted. [PostgreSQL serial types](https://www.postgresql.org/docs/current/datatype-numeric.html#DATATYPE-SERIAL), [identity columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html).

### Selected approach

Use `GENERATED BY DEFAULT AS IDENTITY` for the three columns. This supports automatic IDs for future checkout operations while retaining flexibility for controlled explicit-ID inserts. The existing primary keys remain in place to enforce uniqueness. The selection does not mean every import can proceed without sequence maintenance.

### Implementation

[checkout.sql](../checkout.sql) adds the three identity definitions. An omitted ID, or `DEFAULT`, draws from the column's implicit PostgreSQL sequence; a supplied ID takes precedence under `BY DEFAULT`. [PostgreSQL identity columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html).

Sequence allocation is atomic across sessions, so concurrent requests receive distinct generated values without calculating a shared table maximum for every insert. [PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html).

The migration calculates starting values from the loaded data instead of hard-coding the observed maxima. A different fresh extract can have different IDs, so fixed constants could collide or reserve too little space.

| Expression | Role in this migration |
|---|---|
| `pg_get_serial_sequence(table, column)` | Finds the actual sequence attached to each identity column instead of constructing its name. It supports identity columns despite its historical name. |
| `MAX(...)::bigint` | Finds the loaded maximum and widens arithmetic before adding one. |
| `COALESCE(MAX(...), 0)` | Uses zero when a maximum is `NULL`, such as for an empty table. |
| `GREATEST(...)` | For orders, selects the higher of existing order IDs and order IDs referenced by items. |
| `setval(sequence, calculated_start, false)` | Sets the sequence state so its first allocation returns the calculated starting value. |

`pg_get_serial_sequence()` returns the internally associated sequence for an identity column. [PostgreSQL system information functions](https://www.postgresql.org/docs/current/functions-info.html#FUNCTIONS-INFO-CATALOG-TABLE).

The third `setval()` argument is `false` because the calculation already includes `+ 1`. The first `nextval()` will return that exact value; `true` would advance before returning. [PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html).

### Historical orphan protection

The diagnosis found **692 order items referencing nonexistent orders**. These are item rows, not necessarily 692 distinct missing orders. The preliminary check recorded:

| Metric | Value |
|---|---:|
| Maximum existing order ID | 659384 |
| Maximum order ID referenced by order items | 999862 |
| Maximum order item ID | 1236559 |
| Maximum inventory log ID | 982487 |

The order starting value is `GREATEST(COALESCE(MAX(orders.order_id), 0), COALESCE(MAX(order_items.order_id), 0)) + 1`, evaluated through the subqueries in the migration. For this load, that is **999863**. The other calculated starting values are **1236560** for order items and **982488** for inventory logs.

Starting orders at 659385, just above the existing order maximum, would allow future IDs to enter the range containing historical missing-order references. If a new purchase received one of those referenced IDs, an old orphaned item would appear to belong to that unrelated purchase. Starting above both maxima avoids that accidental association for the historical references present at migration time. It preserves the evidence without inventing missing orders or deleting items.

### Transaction, lock, and execution scope

The migration uses `BEGIN` and `COMMIT` and acquires an `ACCESS EXCLUSIVE` lock on `orders`, `order_items`, and `inventory_log` before changing the schema or calculating maxima. This keeps the related schema changes together and holds the locks through initialization, preventing concurrent table writes from invalidating either the existing-ID or referenced-ID boundary. Table locks are held until transaction end. [PostgreSQL LOCK](https://www.postgresql.org/docs/current/sql-lock.html).

`ACCESS EXCLUSIVE` also blocks ordinary reads and other table access from concurrent transactions. Production deployment would therefore need an appropriate maintenance window. This migration lock is separate from the still-undecided checkout concurrency strategy. [PostgreSQL table-level locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-TABLES).

The migration is intended to run **once after a fresh schema and data load**. `ADD ... AS IDENTITY` is not idempotent and fails for a column that is already an identity. Reinitializing a used sequence without a separate migration plan could reuse previously allocated values. Sequence changes also have distinct rollback semantics: `setval()` on an existing sequence is not undone by rollback. [PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html).

### Trade-offs and limitations

- Failed or rolled-back transactions can leave gaps in allocated sequence values. IDs identify records and do not need to be consecutive. [PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html).
- Explicit IDs remain possible under `BY DEFAULT`. Future imports supplying IDs must account for sequence synchronization and, for orders, historical item references. Importing an explicit ID does not automatically advance its sequence.
- Identity generation alone does not validate customer or product references, repair historical records, create an audit trail, or prevent overselling. Those requirements need their own implementation and verification.
- Existing row values are preserved by this migration; the original schema and confidential extracts remain the historical baseline.
- The columns remain `integer`, with a maximum positive value of 2,147,483,647. Casting maximum-ID calculations to `bigint` does not expand the columns' capacity. [PostgreSQL integer types](https://www.postgresql.org/docs/current/datatype-numeric.html#DATATYPE-INT).
